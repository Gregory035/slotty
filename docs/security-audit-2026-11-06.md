# Аудит безопасности и неисправностей Slotty

Дата: 6 ноября 2026 года. Проверка исходников текущего checkout, существующих unit-тестов и публичных HTTP-ответов production. Это не сертификат безопасности и не полноценный pentest.

## Исправления: первый этап (история)

После согласования локально исправлены пункты 1, 2 и 5:

- Обновление предоплаты получает обязательный membership. Для EMPLOYEE условие employeeId входит непосредственно в запрос обновления; сотрудник без привязки к специалисту получает отказ.
- Ответы изменения статуса и предоплаты скрывают телефон, Telegram ID и username для EMPLOYEE.
- Неудачный checkout больше не включает grace. Льготный срок доступен только платежу автопродления и рассчитывается от renewalForPeriodEndAt, а не от даты обработки ошибки. Обновление ограничено тем же оплаченным периодом, поэтому поздняя ошибка старого платежа не меняет новый период.
- Проверены lint, typecheck, 115 API + 55 web unit-тестов и сборка API. Добавлены проверки ограничения записи по специалисту, редактирования контактов и позднего неуспешного продления.

Пункты 3 и 4 пока не исправлены. Docker/integration/E2E в этом этапе не запускались. Коммит, push и deployment не выполнялись; production всё ещё требует публикации исправлений. Доказательства ниже описывают состояние до исправления; номера строк могли сдвинуться.

Краткий результат: подтверждены пять проблем: две ошибки разграничения прав, обход срока подписки, общие лимиты запросов за прокси и отсутствие защитных заголовков кабинета. Продуктовый код и production не изменялись. Локальные незакоммиченные изменения лендинга сохранены.

## 1. Высокий приоритет: сотрудник может менять предоплату чужой записи внутри компании

- Правило: серверная проверка прав на конкретный объект (OWASP Authorization).
- Доказательство: `apps/api/src/appointments/appointments.controller.ts:131–139` разрешает действие через `APPOINTMENTS_STATUS`, доступное EMPLOYEE в `apps/api/src/companies/company-permission.ts`. Контекст сотрудника не передаётся. `appointments.service.ts:760–781` обновляет запись по `id_companyId` без проверки `employeeId`.
- Условия: авторизованный сотрудник компании знает UUID записи другого специалиста. UUID не является заменой проверки прав. Между разными компаниями эта конкретная операция ограничена companyId.
- Последствие: сотрудник может выставить PAID или WAIVED чужому визиту; ответ также содержит контактные данные клиента.
- Исправление: отдельное разрешение для финансовых действий; либо явно ограничить разрешённое действие собственными записями. Передавать membership и проверять принадлежность до обновления. Добавить негативный API-тест с двумя сотрудниками.
- Статус: подтверждено цепочкой controller → guard → permissions → service; реальные записи не изменялись.

## 2. Высокий приоритет: отменённая оплата открывает новый льготный период без оплаты

- Правило: целостность бизнес-логики оплаты.
- Доказательство: `apps/api/src/billing/billing.service.ts:325–335` при FAILED и отсутствии/истечении оплаченного периода устанавливает PAST_DUE и graceEndsAt = now + 7 дней. `paymentStatus` в этом же файле относит canceled к FAILED. `apps/api/src/billing/entitlements.service.ts:101–116` признаёт такой период активным.
- Условия: настроенная YooKassa, созданный checkout и подтверждённая провайдером отмена/неуспех. Подделывать webhook для этого не требуется. Для каждого нового платежа льготный срок вычисляется заново; существующий grace не проверяется.
- Последствие: завершившийся trial или подписка могут снова получать доступ без оплаты, с повторным сдвигом срока при новых неудачных платежах. Это не означает автоматического повышения тарифа до PRO.
- Исправление: grace только для возобновления ранее оплаченной подписки и один раз на оплаченный период. Отмена первой покупки не должна менять entitlement. Проверить и гонку успешного/неуспешного платежа.
- Статус: подтверждено логикой кода; реальные платежи не создавались, эксплуатация на production не проверялась.

## 3. Средний приоритет: ограничитель запросов считает разных посетителей одним IP

- Правило: EXPRESS-PROXY-001.
- Доказательство: `apps/api/src/main.ts:11–68` не настраивает trust proxy; `apps/api/src/rate-limit/rate-limit.guard.ts:72` использует request.ip. `apps/web/nginx.conf:26–31` проксирует запросы и заменяет X-Forwarded-For на remote_addr. В production API доступно через Nginx, а не напрямую.
- Последствие: посетители за одним экземпляром прокси делят лимиты входа, регистрации и сброса пароля. Значения по умолчанию: 5 входов/минуту и 3 регистрации/час. Один посетитель способен исчерпать общий лимит; это объясняет возможные необоснованные 429.
- Исправление: согласовать доверенную цепочку Caddy → Nginx → Express и сохранить проверенный клиентский IP. Не включать безусловное trust proxy=true. Добавить интеграционный тест двух IP и поддельного X-Forwarded-For через прокси.
- Статус: подтверждено конфигурацией; лимиты production намеренно не исчерпывались. Фактические значения переменных окружения сервера в этом аудите не читались.

## 4. Средний приоритет: у кабинета отсутствуют защитные заголовки

- Правило: REACT-HEADERS-001.
- Доказательство: `apps/web/nginx.conf:15–18` задаёт защитные заголовки на уровне server, но location `/app` и приватные маршруты переопределяют add_header (`:67–110`). Проверка HTTPS production: `/` возвращает CSP, nosniff, Referrer-Policy и Permissions-Policy; `/app` возвращает 200 без всех четырёх. X-Frame-Options также отсутствует. Ответ 404 имеет ту же проблему.
- Последствие: кабинет лишён защиты CSP и запрета встраивания во внешний iframe. Это ослабление защиты и предпосылка clickjacking, а не доказанная XSS.
- Исправление: общий include защитных заголовков для всех соответствующих locations; сохранить разрешённое встраивание Telegram Mini App отдельно. Добавить проверки реального Nginx, а не только dev-сервера.
- Статус: подтверждено на production 6 ноября 2026 года.

## 5. Средний приоритет: изменение статуса раскрывает скрытые контакты клиента

- Правило: минимизация выдаваемых данных / авторизация полей.
- Доказательство: `apps/api/src/appointments/appointments.service.ts:517` скрывает контакты для EMPLOYEE при получении списка. `:663–665` ограничивает изменение статуса собственным визитом, однако `:757` возвращает `toResponse(appointment)` без редактирования. `:1163–1189` по умолчанию раскрывает phone, username и telegramId.
- Условия: сотрудник меняет статус своей записи. Ему не нужно знать чужой UUID.
- Последствие: контакты, скрытые в списке по роли, становятся доступны в ответе операции. Отдельно от проблемы №1.
- Исправление: применять одну политику сериализации по роли во всех ответах, включая мутации; добавить тест отсутствия контактов в ответе EMPLOYEE.
- Статус: подтверждено по коду; персональные данные production не запрашивались.

## Проверки и ограничения

- `npm run lint` — успешно.
- `npm run typecheck` — успешно.
- Unit-тесты: API 113/113, web 55/55. Их успех не покрывает описанные негативные сценарии.
- Production: главная 200; кабинет `/app` 200; `/api/health/ready` 200 и status=ok (PostgreSQL/Redis); `/api/companies` без авторизации 401; неизвестный URL 404.
- `npm audit --omit=dev --json`: 8 записей (3 HIGH, 5 MODERATE), 0 CRITICAL. Три HIGH относятся к одной цепочке deepmerge-ts → @prisma/config → prisma. Dockerfile явно удаляет эти пакеты из API runtime; нельзя называть это тремя эксплуатируемыми уязвимостями API. Есть MODERATE в цепочке Sentry/glob/minimatch и qs; достижимость опасных функций из пользовательского запроса не доказана. Требуется отдельное обновление с проверками, не npm audit fix --force.
- Docker daemon локально недоступен. Integration/E2E с отдельной БД, контейнерная сборка и Trivy в этом запуске не выполнялись. Не использовалась рабочая БД вместо тестовой.
- Не проводились нагрузочные атаки, подбор паролей, реальные списания, изменение аккаунтов или отправка уведомлений.
- Неподтверждённые предположения о конкурентном бронировании, приглашениях и SSRF не включены в список подтверждённых уязвимостей.

## Порядок исправления

1. Права на предоплату и единое скрытие контактов.
2. Правила льготного периода подписки.
3. Определение клиентского IP за прокси.
4. Заголовки кабинета и негативные HTTP/API-тесты.
5. Разбор обновлений зависимостей и повторный аудит после исправлений.
